# 0019. Database access, migrations at startup, audit in the same transaction

- Status: Accepted
- Date: 2026-09-28
- Refines: [0007](0007-persistence.md)

## Context

ADR 0007 chose SQLite in WAL mode with one writer per file. Implementing it raised four
questions:

- How exactly connections are managed.
- When migrations run.
- How audit events stay consistent with the changes they describe.
- How slow work, such as password hashing, interacts with transactions.

## Decision

1. **One connection per database file** (`pool_size=1`, `max_overflow=0`). Every transaction
   in the process is serialized per file, which has three effects:
   - SQLite lock-upgrade failures between our own transactions (`SQLITE_BUSY` on
     deferred-to-write upgrades) can't happen.
   - The audit chain's "read the last hash, append the next" step is atomic.
   - External readers (the backup API, `audit-verify`) still work concurrently thanks to WAL.
2. **One session per request.** FastAPI caches the session dependency per request, so the
   authentication dependency and the handler share it. Opening a second session inside a
   request would wait for the only connection forever; this is documented in `api/deps.py`.
3. **No slow work inside a transaction.** Before Argon2 hashing or verification, and in
   future before any I/O to aircraft, the handler commits or ends its transaction. The
   connection goes back to the pool while the slow work runs.
4. **Audit in the same transaction as the change.** `services.audit.record` appends inside
   the caller's transaction, so a change and its audit event commit or roll back together.
   There is never a change without a record, or a record without a change.
5. **Migrations run at startup**, and through `fleet-service db upgrade`:
   - Alembic runs with one script directory per database, a synchronous `sqlite://`
     connection and batch mode.
   - If `ops.db` has data and a migration is pending, it is first copied with the SQLite
     online backup API to `data/backups/ops-<revision>-<UTC>.db`.
   - Migrations are forward-only. `downgrade()` raises and points at the backup.
6. **Timestamps come from the injected clock, never database defaults.** They are stored as
   fixed-width UTC text through `UTCDateTime`, which rejects naive datetimes.
7. **Revision ids are sequential** (`0001`, `0002` …), and autogenerated migrations are
   formatted by ruff.

## Alternatives considered

- **Connection pool with `BEGIN IMMEDIATE`:** allows parallel reads, but it adds lock handling
  for no measurable benefit at a few operators. Read-only connections can be added later for
  long replay queries (M5).
- **Separate audit writer task or queue:** it would decouple audit latency, but a crash could
  leave a change without its record, which is unacceptable for an audit trail.
- **Manual migrations only:** field teams would forget. Running at startup with an automatic
  backup is safer.

## Consequences

- Throughput is bounded by serialized transactions, which is ample for this scale. The M5 load
  tests will confirm it.
- Handlers must follow rules 2 and 3. Code review and the tests (`get_principal` commits
  before the handler runs) enforce them.
